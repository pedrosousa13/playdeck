# Structural components

These wire the player together and are exercised implicitly by every other
story rather than shown in isolation.

- **`Player.Root`** — owns the `PlayerController`; its imperative handle is the
  controller. Props include `loading` (`eager` | `viewport` | `interaction`),
  `loadMargin`, `preload`, `autoplay`, and native playback options.
- **`Player.Viewport`** — the layout box controls compose into; registers with
  the controller for viewport-triggered activation.
- **`Player.Media`** — mounts the actual media element once a provider attaches.
  The mock-backed stories issue no media; it renders for real in the
  `Real playback/Providers` and `Fixtures/PlayerFixture` stories.

## Commands before the player is ready

A command issued before the player is ready is **refused, not queued**. It
resolves `{ ok: false, reason: 'not-ready' }`, and nothing replays it later.

That window is reachable in ordinary code. `Player.Controls` and its buttons
render unconditionally, so they are on screen and clickable while the provider
is still loading — `Player.PlayButton` included, and it is refused like
everything else in that window. The one control that behaves differently is
`Player.ActivationButton`, which owns the activation path and queues the play
it triggers; it is `aria-disabled` while the provider loads.

So "apply my preferred rate as soon as the player mounts" runs squarely inside
the refusal window. Await `whenReady()` first:

```tsx
const player = useRef<Player.PlayerHandle>(null);

useEffect(() => {
  void player.current?.whenReady().then((ready) => {
    if (ready.ok) void player.current?.setPlaybackRate(0.75);
  });
}, []);
```

It resolves `{ ok: true }` once the player reaches its `ready` activation, which
is the point where a command is actually accepted. Not on provider attach:
YouTube and Vimeo build their underlying player inside `load()`, so an attached
adapter still answers `not-ready` — resolving there would be true for the native
provider alone.

It resolves `{ ok: false }` rather than hanging when readiness becomes
impossible — `provider-error` for a terminal failure, `not-ready` if the player
is torn down while you wait. A _recoverable_ error does not settle it, because
the React layer reports one for a source that has not arrived yet
(`source={data?.url ?? ''}`), and that heals on the next render.

Available on the ref handle and on `usePlayerActions()`. Inside a component you
can equally watch the state, which needs no new API:

```tsx
const activation = usePlayerState((state) => state.activation);
useEffect(() => {
  if (activation === 'ready') void actions.setPlaybackRate(0.75);
}, [activation, actions]);
```

`whenReady()` earns its place on the imperative handle, where there is no
render loop to hang that effect on — `on('ready', …)` is edge-triggered and
misses a listener attached after the fact, and `subscribe()` fires
synchronously during subscription, which makes unsubscribing from the first
call awkward.
