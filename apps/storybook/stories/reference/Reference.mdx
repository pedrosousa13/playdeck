# Reference example

One composed player, in `stories/reference/`, assembled **only** from public
`@reely/react` and `@reely/core` exports. It is the runnable proof behind
criterion 8 of #1, and it is the artifact #32 points axe and its keyboard flows
at.

Two mountings of one component, so there is a single composition rather than
two that drift:

- **`Reference/Player → Composition`** — under the mock decorator, every
  capability dialed available, no media and no network. It runs in
  `pnpm --filter @reely/storybook test` with axe at `test: 'error'`.
- **`Reference/Player → RealSources`** — tagged `real-playback` and `!test`, so
  the decorator steps aside and the story owns its own `Player.Root`. This is
  what `e2e/reference.spec.ts` drives.

## Icons are your job, not the library's

Every button here receives an icon child from `@reely/react`'s icon exports.
The primitives keep their text fallbacks (`children ?? (isPlaying ? 'Pause' :
'Play')`) and are unchanged by this example. Defaulting to icons would make
every icon a static dependency of every button and undo the opt-in
tree-shakeability the icon exports exist for.

Accessible names are unaffected either way: they come from each primitive's own
`aria-label`, never from the child. Supplying icon children _is_ composition
from public parts, which is the thing being proved.

## Layout is your job too

The layout CSS lives in this example, not in `@reely/react/theme.css`. The
library stays unopinionated about layout; this example documents one way to lay
a control row out — two rows, a wrapping button row, and the volume slider
dropped below a 420px breakpoint so the composition stays usable at 320px.

That breakpoint is a **container query**, not a media query: it asks how wide
the _player_ is, so an embed in a narrow column gets the same treatment as a
narrow phone. Only that rule is container-driven. The box's own `aspect-ratio`
and the control row's switch from overlay to in-flow stay on a viewport media
query, because they are a pair — the row can only leave the overlay once the box
has given up its fixed ratio — and an element cannot query its own container
anyway. Splitting the pair across two queries lets them disagree, which is the
35px of clipped controls #32 measured.

`@container` is Chrome 105, Firefox 110 and Safari 16 — newer than the floor the
packages declare (Chrome 99, Firefox 97, Safari 15.4). That does not move the
packages' floor: this is a composition in this workbench, never published, and
the primitives ship no CSS at all.

Where a primitive sets geometry on itself, your `style` prop overrides it —
see the `style` section of `Overview/Contract` for the one carve-out.

This example does **not** mount `@reely/react/theme.css`. The only per-story way
to mount it in this repo reads it by path out of `packages/`, which the import
rule below forbids, and a plain side-effect import would leak the theme into
every other story's document.

## What the story mounting does not prove

`Player.Media` renders nothing in the `Composition` story, on purpose.
`Media` is gated on activation, and every route to activation loads a real
provider that replaces the mock adapter — so a mock-owned story and a mounted
media element are mutually exclusive. The media layer, the `<track>` declared
through `Media`'s `textTracks`, the provider swap and the quality ladder are all
proved by `RealSources` and `e2e/reference.spec.ts` instead.

## "Public exports only" is a lint rule

`eslint.config.js` scopes a `no-restricted-imports` block to
`stories/reference/**`. Rejected: any `../` escape, anything under
`packages/`, any `@reely/*/src/*` subpath, the provider packages, and
`hls.js`. It runs in the existing `static` gate, so a violation fails at
authoring time. Convention has already failed twice (#15, #73).

`stories/reference/import-rule.contract.test.ts` runs ESLint over both halves of
the rule — the specifiers it must reject and the ones it must accept. A lint
rule that has never been seen to fail is worth nothing.

Two stated limitations:

- **Specifier hygiene, not packed-entry coverage.** Storybook aliases
  `@reely/react` to `packages/react/src/index.tsx`, so this rule cannot prove
  the _published_ entry exports what the example touches. That side is covered
  where it belongs: `attw` and `publint` in `test:packages`, plus
  `packages/react/test/theme.test.ts` asserting the exports map.
- **Not a dependency allowlist.** ESLint's group negation never un-matches a
  specifier containing a slash, so the allowlist form of this rule rejects
  `@reely/react` itself. The denylist that works stops reaching into internals;
  it will not stop a brand-new third-party dependency being added.

## Capability gating, on display

Switching sources makes gating visible rather than hidden, which is the
primitives' central promise:

- **`AirPlayButton` disappears on YouTube and Vimeo.** Both hard-code the
  `airPlay` capability unavailable, so the control renders nothing.
- **`PipButton` disappears on YouTube, but not on Vimeo.** YouTube hard-codes
  `pictureInPicture` unavailable; Vimeo reports it available up front and
  downgrades only if a request actually fails. So the same composition shows a
  PiP button on one iframe provider and not the other, without the example
  branching on provider anywhere.
- **The quality group appears only under HLS, on browsers that resolve to
  hls.js.** Only the hls.js engine populates `PlayerState.qualities`. The
  example no longer forces an engine, so each browser resolves HLS via its own
  `canPlayType`: MP4 never has a quality ladder regardless, and neither does
  HLS on a browser that reports native HLS support — which, measured
  directly, is Chromium and WebKit both, leaving Firefox as the one where the
  menu section actually appears.

The lesson for anyone testing against these: a capability assertion needs an
explicit settle condition only when the capability's _initial_ value differs
from its settled value. Statically-unavailable capabilities are safe to assert
immediately; a defaulted-available one like Vimeo's `pictureInPicture` is not.

## The gap this example found before a line of code

Composing the settings menu revealed that nothing in public state enumerated the
selectable quality ladder — `PlayerState.quality` was the level playing now, and
`selectQuality` took a height nobody could discover. That was filed as #81 and
landed on its own terms before this example.

Driving the example against a **local** fixture then surfaced a second one, #86:
a queued user play could be dropped. Every existing end-to-end test routed its
media through a mocked response, which added just enough latency to hide an
ordering bug; a real local file did not. It is fixed. A third, #87, is the same
defect for audible autoplay one layer down, and is filed but not fixed here.

Two gaps in one example is the argument for having it. Neither was reachable
from unit tests that mock the thing being tested.

## What #32 verifies here, and where

Two axe runners, deliberately. `.storybook/preview.tsx` sets
`a11y: { test: 'error' }`, so axe fails the Vitest story run on any violation
for **every** story, primitive and composed — that is the authoring-time gate,
and it is Chromium-only because `apps/storybook/vitest.config.ts` pins one
browser instance. `e2e/a11y.spec.ts` adds `@axe-core/playwright` over the
composed example's seven states in Chromium, Firefox and WebKit, scoped to
`[data-reely-part="viewport"]` so Storybook's own iframe chrome can never enter
a result.

The seven states are five stories: `Composition` is genuinely both _paused_ and
_captions-on_, and _menu-open_ is that same story with the menu opened by the
spec. `Idle`, `Playing`, `BlockedAutoplay` and `ErrorState` stage the rest
through the mock decorator.

**No axe rule is suppressed anywhere.** One finding was a real primitive bug,
fixed rather than worked around: `Player.LoadingIndicator` kept its live region
mounted while idle — deliberately, so a screen reader announces the
loading/buffering transition — but did so as a full-bleed
`position: absolute; inset: 0; z-index: 30` box. Even empty and
`pointer-events: none`, that geometry alone made axe unable to resolve a
background colour for **any** text in **any** reely viewport, for every
consumer. It now renders visually-hidden while idle and takes the full-bleed
overlay only once there is something to show; its own tests live in
`packages/react/test/activation.test.tsx`. `SettingsMenuContent`'s
`tabIndex={0}` is the other precedent: a real `scrollable-region-focusable`
violation, remediated rather than silenced.

Axe runs its **default rule set**, not a narrower WCAG-tag subset — scoping
with `withTags` would silently drop the best-practice rules, which is a
suppression by another name. That choice has a cost worth stating plainly:
`.include('[data-reely-part="viewport"]')` sets axe's context to the player
subtree, so page-level rules (`bypass`, `region`, `landmark-one-main`,
`page-has-heading-one`) never run against it — those are properties of
Storybook's bare iframe document (no `<main>`, no `<h1>`, no landmarks), not of
reely, and a consumer's real page owns them. A clean run here is a claim about
this subtree, not about a host page.

Every state also asserts `results.incomplete` — axe's needs-review bucket —
against a per-state allowlist of rule ids, compared by equality, so an
undiagnosed new finding fails the same as a violation would. Three states
carry a diagnosed entry, not an ignored one:

- **`idle` and `error` — `color-contrast`.** `ActivationButton` and
  `ErrorDisplay` are both real, full-viewport surfaces while shown
  (`position: absolute; inset: 0`, not overridable through their `style` prop
  — filed as #89), and each outranks the time row underneath it. Axe reports
  the resulting stacking-order overlap as an unresolvable color-contrast case;
  no CSS change in this example fixes it.
- **`menu-open` — `aria-valid-attr-value`.** axe-core flags any
  `aria-controls` paired with a non-false `aria-haspopup` as needs-review the
  instant the attribute is present, without resolving the id first. Every
  correctly-built `aria-haspopup` + `aria-controls` menu trips this — a
  permanent axe-core limitation for the pattern, not something fixable here.

The other four states assert both buckets empty.

### Reflow

Three tests, because WCAG 1.4.4 (200% text) and 1.4.10 (320 CSS px) are
separate criteria and neither implies the other: 200% at 1280px, 320px at
normal text, and — beyond what either criterion demands — 320px at 200%. That
last one is where this composition actually broke: the control row grew to
179px inside a 144px `aspect-ratio: 16/9`, `overflow: hidden` box and lost 35px
off the top.

Below 420px the control row now takes `position: relative` rather than
staying an absolutely-positioned overlay, so it occupies real space and the
viewport is free to size around it — not `position: static`, which is what
this fix first shipped as and was a real bug: `static` also drops an element
out of the positioned stacking context its own `z-index: 20` depends on, so
the row silently painted **below** Gestures/Poster/Media instead of above
them — invisible and unclickable at ≤420px, with every existing assertion,
including a plain `toBeVisible()`, still green. Each reflow case now
hit-tests the play button's own center with `elementFromPoint` and asserts it
resolves to the button itself, not to whatever got painted on top of it —
correct geometry alone already shipped this regression once, so it is no
longer trusted alone.

### Announcements

The policy is _state transitions only_ — never time updates, never per-cue.
Asserted twice, because either alone is weak. Structurally, in the
`LiveRegionInventory` story: the composed example puts exactly
`loading-indicator` and `captions-announcer` in the tree, and neither `Time`
nor `Captions` carries live semantics. Behaviourally, in
`e2e/a11y-media.spec.ts`: a `MutationObserver` over every live region records
nothing across a full clip with its cue window, then exactly one entry when
captions are toggled.

That behavioural check needed its own fixture, `captions-reference.vtt`, with
a cue boundary at 0.4s inside the reference example's ~1s clip. The
composition's existing `captions-en.vtt` is a single 0–5s cue, so on a clip
this short no cue transition would ever occur inside the observation window,
and the "never per-cue" half of this criterion would go unexercised without
ever failing.

### Keyboard

The suite is split both by what each mounting can prove and by media
dependency. `e2e/a11y.spec.ts` holds the mock-based checks (the axe sweep,
reflow and hit-test, tab order, menu focus); `e2e/a11y-media.spec.ts` holds
the real-media checks (shortcut effects, the announcement behavioural test) —
kept apart because a real-media timing flake must never read as a regression
in the deterministic mock suite, or vice versa. Both filenames contain "a11y",
so `pnpm test:e2e --grep a11y` still catches both.

Tab order and menu focus return run against the mock `Composition`, the only
mounting where a fixed expected order is honest — every capability is dialed
available, so all nine controls render on every engine, whereas on real MP4
`AirPlayButton` appears on WebKit alone. Shortcut _effects_ run against
`RealSources` and are read off the media element: the mock adapter implements
no `seek` and echoes no state, so a shortcut assertion there could not tell a
wired handler from a deleted one.

The tab walk stops at `fullscreen-button`. Past the last control the engines
diverge — Chromium and WebKit move focus to the browser chrome, Firefox under
Playwright stays put — which is harness behaviour, not a focus trap.

### Not covered here

`pnpm test:e2e --grep a11y` green does **not** close #32. The owner's visual
review of the composed example plus the primitive stories across
wide/narrow/touch layouts is a human gate, scheduled after #17's real-device
matrix — the automated pass above is necessary, not sufficient, and should
never be read as the whole criterion. Capability-transition focus restoration
is unit-tested in `packages/react/test/controls.test.tsx` rather than here,
because #32 asks for focus retention through menu open/close specifically.

The two `color-contrast` diagnoses above have a shared root cause that is
filed, not fixed, here: `ActivationButton` and `ErrorDisplay` both apply their
full-bleed geometry after spreading the consumer's own `style` prop, so
neither can be repositioned by a consumer either — tracked as #89.
