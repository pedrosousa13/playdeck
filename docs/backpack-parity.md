# Backpack parity matrix

One row per story in EF Backpack's three video story files — `Video.stories.tsx`,
`AutoplayVideo.stories.tsx` and `VideoHoverPreview.stories.tsx` — recording
whether the `BackpackVideo` wrapper in `apps/storybook` reproduces it on Reely
primitives. The wrapper reimplements Backpack's `VideoPlayer` prop API so that
Backpack's own story args copy across near-verbatim; it exists to prove the swap
is possible, not to ship, so parity here means behavior, not pixels.

- `full` — a Reely story reproduces the Backpack story with the same args.
- `partial` — a Reely story exists, but something the Backpack story shows is
  not reproduced. The note says what.
- `gap` — no Reely story yet. The note names the one issue that closes it.

Counts: 38 rows — 34 `full`, 4 `partial`, 0 `gap`.

A converted row means the wrapper attaches a real provider for it, not that it
renders under the workbench's mock. Each converted component has a pair of story
suites for that: `Backpack parity/Mock/*` covers behavior deterministically
against the mock, and `Backpack parity/Real/*` is where the provider actually
attaches.

**Backpack's stories are the scenario catalogue; its implementation is not a
specification** ([ADR-0003](adr/0003-backpack-is-a-scenario-source-not-a-spec.md)).
A copied behavior has to survive review on its own merits, and where Backpack's
answer is wrong Reely does it properly — recorded under "Deliberate divergences"
below, which also names where Reely is currently the worse of the two. Line
references point into the Backpack v4 beta checkout
(`apps/backpack/beta`); v3 is stale for this work.

## Running the harness

`pnpm test:parity` checks the two sides against each other for real, through
`playwright.parity.config.ts`. The tables below are its input rather than a
description of it: it parses them into a pair list, resolves every story name
through both Storybooks' `/index.json`, and measures the two sides with one
function, so a difference cannot come from two ways of measuring. It serves both
Storybooks itself — Reely's on 4173, Backpack's on 6007 — and reuses either that
is already up, which leaves one local prerequisite: a Backpack v4 beta checkout
(`@ef-global/backpack` `4.5.0-beta.19`) for the second of them.
`REELY_BACKPACK_DIR` names it, defaulting to
`/Users/pedrosousa/Documents/apps/backpack/beta`, and a missing directory fails
at config load rather than half way through a sweep. A full sweep takes about
nine minutes, which is what `PARITY_PAIR_RANGE` (`0-6`, say) is for. Nothing
runs it in CI, deliberately: that checkout is a prerequisite CI has none of.

It fails today, and a first run should read that as the harness working rather
than as a broken setup, for two reasons at once. The sweep found 97 undeclared
divergences across the 26 pairs it can measure, and the measurement check
asserts there are none: only a divergence declared in
`e2e/parity/declared-divergences.ts`, against a sentence in this file or an ADR,
goes through quietly. The same check also fails on two rows below whose story
names no longer resolve to anything in Backpack's `/index.json` —
`CustomCoverImage` and `SocialCarouselAtomIntegration` — because a name this
file records that no Storybook serves is drift in this file, and the harness
reports it rather than quietly measuring 36 rows and calling it 38. Both are
reported together at the end of a run, after every pair that could be measured
has been. Two limits are worth knowing
before reading a result. It compares measurements and not pixels, for the reason
this file opens with — the wrapper reproduces Backpack's behavior, not its
styling stack, so a pixel diff would be red on every row and would say nothing —
and the single masked screenshot it takes is on the real-playback side, Reely
against itself, with no Backpack image in it at all.

## Deliberate divergences

Every entry below was read against the source rather than inferred. Three claims
in the first pass at this list turned out to be wrong about Backpack's behavior;
the corrections are recorded here rather than dropped, because the shape of the
mistake is worth keeping.

The `Player.Poster` row is the one entry in either table with no issue behind it,
and it is here rather than under "Where Reely is better" because it is honestly a
Reely limitation — it shaped SIDEPRO-204's design rather than being worked around
by it. It is also not obviously a defect to fix: a poster that returned by default
would flash back over every ordinary paused video, so the primitive is right for
its main case and wrong for this one. What would close it is a way for a consumer
to say which it wants, and nothing about the hover-preview composition needs that
before it works. Recorded so the duplicated cover layer reads as a decision rather
than as an oversight.

Backpack's `light` defaults to `true`; the wrapper's defaults to `false`. The
wrapper's loading strategy is already `interaction` regardless of `light` — it
never mounts the player before activation — so `light: true` here only adds a
thumbnail image on top of that, fetched from a third-party endpoint on every
mount. Defaulting it on would add a network request nothing asked for, so the
wrapper opts a caller in instead. A story whose cover is fetched from that
endpoint, or whose `placeholderImageSrc` is a real remote image, lives under
`Backpack parity/Real/Video` rather than `Backpack parity/Mock/Video`, because the
deterministic suite must stay offline.

The play icon's default size changed with SIDEPRO-202, so every story in both
suites looks different for it. The wrapper drew a 4rem icon unconditionally,
which is Backpack's `xl` rather than its default `m`; honouring `playIconSize`
makes the resting icon 3rem, the box `VideoPlayIcon` maps `m` to
(`VideoPlayIcon.tsx:22-39` → `Icon/icon-wrapper.styles.ts:46-48`, against `xl`'s
`size-16` at `:52-54`). Nothing asserted the old size, so the change cost no
test — it is visible, and it is the correct size.

`variant` and `playIconSize` carry two values each where Backpack has four.

The deterministic stories in this file are the one place in the parity suite that
cannot carry Backpack's own `url`. Everywhere else a real provider URL is inert
because nothing ever commits it — `BackpackVideo` loads on interaction, and no
deterministic story clicks the activation button — but loading when the player's box
scrolls into view is the whole point of this composition, so a resolvable source on screen is
committed with nothing clicked at all. The first revision of these stories
carried `https://vimeo.com/336066147` and the suite's own no-external-request
guard caught the consequence: Vimeo's oEmbed resolve, then a `player.vimeo.com`
iframe. They pass an unresolvable `mock://` source instead and stage a provider
straight onto the controller, which is also what makes any playback observable
offline. Both of those bypass activation, so _when_ a provider attaches is left
to `backpack-autoplay-video.contract.test.ts` — which drives an activation
observer directly against a source it never intersects — and to
`Backpack parity/Real/AutoplayVideo`, where it happens for real.

`threshold` now reaches both halves of an autoplaying video. Backpack drives the
start and the off-screen pause from one observer, so its `threshold` governs
both. Here they stay two observers with two owners, but each honours the same
prop: `Player.Root` carries `loadThreshold` alongside `loadMargin`
(`root.tsx:63`), and `BackpackVideoInternal` forwards `threshold` into it
(`backpack-video.tsx:558`) as well as into the pause observer. Before that,
Reely's activation observer took a `rootMargin` and no threshold, so a
`threshold` above `0` fired the start at the first visible pixel while the pause
hook called the video out of view and paused it again at once — one spurious
play/pause pair, both reported through `onPlayChange`.
`Backpack parity/Real/AutoplayVideo → InPage` is where the closed gap is
visible: `threshold: 1` there means scrolling starts playback only once the
whole player is on screen. One shape stays outside it by design — a box taller
or wider than the scroll container it moves through can never reach a threshold
near `1`, so it activates at the first visible pixel instead of staying dormant
forever.

One departure from SIDEPRO-203's brief rather than from Backpack, recorded here
because the rest of this file records only the latter. The brief asked the
composition to reuse the existing off-screen-pause observer rather than add a
second one; two run per autoplaying video, and
`backpack-autoplay-video.contract.test.ts` asserts exactly that number on
purpose. They answer different questions for different owners — the activation
observer belongs to `@reely/react` and decides when to load, the pause hook's
belongs to this wrapper and decides when to pause — so serving both from one
would mean the wrapper reaching inside the primitive's own loading decision. The
intent behind the brief's line, that the wrapper adds no observer of its own,
does hold: neither of the two is the wrapper's.

Every deterministic story in this file passes a `placeholderImageSrc`, including
the six Backpack stories that pass none. That is a requirement rather than a
convenience, and it is this file's version of the constraint the
`AutoplayVideo` note above describes. `Backpack parity/Mock/Video` can leave a cover
off because a cover there is `light`'s business and `light` defaults off; this
composition resolves one unconditionally, since a hover preview has a resting
state to draw, and `useVideoThumbnail` fetches the source's oEmbed endpoint
whenever no image is supplied (`video-thumbnail.ts:150-151,168-185`). So a bare
`vimeo.com` URL here is a live request to `vimeo.com/api/oembed.json`, which the
suite's own no-external-request guard fails
(`apps/storybook/.storybook/vitest.setup.ts:47-70`). Backpack's own `url` is
otherwise safe in this file, for the reason it is safe in `Video`'s and one more:
each story stages a provider already reporting `activation: 'ready'`, and
`activateFromInteraction` — which is what a hover would otherwise load through —
returns early for any activation other than `dormant` or a recoverable `error`
(`packages/react/src/use-activation.ts:354`, its `if (activation !== 'dormant')
return`).

`WithCustomDuration` holds its preview through `isHovered` rather than hovering
it, and the reason is worth recording because it is not a test artefact. A click
on a button below the surface moves the pointer off it, which ends the hover,
pauses the video and rewinds it — so a story that hovered and then clicked would
be pressing on a preview that had just stopped, for the automation driver and for
a viewer with a real mouse alike. `isHovered` is Backpack's own prop for exactly
this ("whether the preview is currently being shown", `VideoHoverPreview.tsx:32-35`),
OR'd with the pointer rather than replacing it (`:79`), and no Backpack story
exercises it — so that story is also the only story-level coverage the prop has,
and the only one showing the way in that a touch device has.

`muted` and `loop` are the two props no deterministic story in this file can
observe, and they are graded on different grounds — which is worth spelling out,
because an earlier revision of this table called both `partial` and was wrong
about both. Neither prop reaches anything without a provider, and that suite
attaches none. `WithSound` is `full` because a provider _does_ carry it: Vimeo
implements `mute`/`unmute` and `Player.Root` reconciles the controlled value, so
`Backpack parity/Real/VideoHoverPreview → WithSound` reproduces the Backpack
story — the same footing on which `Light` and `VimeoCoverImage` are `full` with a
real-playback story alone. `WithoutLoop` is `full` for a different and less
comfortable reason: nothing loops on a Vimeo source in Reely at all, so a story
asking for no looping matches by coincidence. The prop's inertness is a behaviour
gap, recorded under "Where Reely is worse" as SIDEPRO-210, and it is invisible in
all nine stories here — including the eight that run with the default
`loop: true`.
