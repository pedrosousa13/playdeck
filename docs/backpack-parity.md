# Backpack parity matrix

One row per story in EF Backpack's three video story files — `Video.stories.tsx`,
`AutoplayVideo.stories.tsx` and `VideoHoverPreview.stories.tsx` — recording
whether the `BackpackVideo` wrapper in `apps/storybook` reproduces it on Reely
primitives. The wrapper reimplements Backpack's `VideoPlayer` prop API so that
Backpack's own story args copy across near-verbatim; it exists to prove the swap
is possible, not to ship, so parity here means behavior, not pixels.

- `full` — a Reely story reproduces the Backpack story with the same args.
- `partial` — a Reely story exists, but something the Backpack story shows is
  not reproduced. The note says what.
- `gap` — no Reely story yet. The note names the one issue that closes it.

Counts: 38 rows — 18 `full`, 3 `partial`, 17 `gap`.

A converted row means the wrapper attaches a real provider for it, not that it
renders under the workbench's mock. `Backpack parity/Video` covers behavior
deterministically against the mock; `Real playback/BackpackVideo` is where the
provider actually attaches.

**Backpack's stories are the scenario catalogue; its implementation is not a
specification** ([ADR-0003](adr/0003-backpack-is-a-scenario-source-not-a-spec.md)).
A copied behavior has to survive review on its own merits, and where Backpack's
answer is wrong Reely does it properly — recorded under "Deliberate divergences"
below, which also names where Reely is currently the worse of the two. Line
references point into the Backpack v4 beta checkout
(`apps/backpack/beta`); v3 is stale for this work.

## Deliberate divergences

Every entry below was read against the source rather than inferred. Three claims
in the first pass at this list turned out to be wrong about Backpack's behavior;
the corrections are recorded here rather than dropped, because the shape of the
mistake is worth keeping.

### Where Reely is worse

| What Reely does                                                                                                                                         | Why it is wrong                                                                                                                                                                                                                                                              | Tracked as  |
| ------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------- |
| `loop` reaches `Player.Root` but never a Vimeo or YouTube provider (`root.tsx:433` → `provider-loaders.ts:22,29` pass it to HLS and native only)        | `loop: true` silently does nothing on the two most common providers. Wistia's provider already implements it (`provider-wistia/src/attachment.ts:204`), so the plumbing is the only missing part.                                                                            | SIDEPRO-210 |
| The thumbnail lookup matches URLs by unanchored substring (`video-thumbnail.ts:16,18`) beside `@reely/core`'s `detectSource`, which parses the hostname | Two sources of truth that disagree: `https://example.com/vimeo.com/1` fires a request at Vimeo's oEmbed for a URL `detectSource` rejects, and `youtube.com/embed/ID` plays but silently shows no cover.                                                                      | SIDEPRO-213 |
| An optimistic cover click plus an `aria-label` override on `Player.ActivationButton` (`backpack-video.tsx:339`, `:311-317`)                             | On an activation error the cover is gone for good, `onPlayChange(true)` has already fired for playback that never happened, and the primitive's own "Retry loading video" label is overridden — so a failed load presents a button announced "Pause video" over a blank box. | SIDEPRO-212 |
| `alt` reaches the DOM but no accessibility tree                                                                                                         | `Player.Poster` is `aria-hidden`, so a caller-supplied `alt` is dead weight rather than a label. Reely's affordance is better named, but the prop should still fold into that button's accessible name.                                                                      | SIDEPRO-214 |
| A thumbnail is refetched on every mount                                                                                                                 | No cross-mount cache; a module-level map keyed by endpoint would close it. Also YouTube's oEmbed returns `hqdefault`, where Backpack's string hack reached a 480px image, so covers are slightly softer.                                                                     | SIDEPRO-213 |

Backpack's `light` defaults to `true`; the wrapper's defaults to `false`. The
wrapper's loading strategy is already `interaction` regardless of `light` — it
never mounts the player before activation — so `light: true` here only adds a
thumbnail image on top of that, fetched from a third-party endpoint on every
mount. Defaulting it on would add a network request nothing asked for, so the
wrapper opts a caller in instead. A story whose cover is fetched from that
endpoint, or whose `placeholderImageSrc` is a real remote image, lives under
`Real playback/BackpackVideo` rather than `Backpack parity/Video`, because the
deterministic suite must stay offline.

The play icon's default size changed with SIDEPRO-202, so every story in both
suites looks different for it. The wrapper drew a 4rem icon unconditionally,
which is Backpack's `xl` rather than its default `m`; honouring `playIconSize`
makes the resting icon 3rem, the box `VideoPlayIcon` maps `m` to
(`VideoPlayIcon.tsx:22-39` → `Icon/icon-wrapper.styles.ts:46-48`, against `xl`'s
`size-16` at `:52-54`). Nothing asserted the old size, so the change cost no
test — it is visible, and it is the correct size.

`variant` and `playIconSize` carry two values each where Backpack has four.
`variant` omits `shadow-s` (`video.styles.ts:21-23`), `shadow-l` (`:27-29`) and
`shadow-xl` (`:30-32`); `playIconSize` omits `s` and `l` (`VideoPlayIcon.tsx:11`).
Each omitted value is one more hand-approximated CSS rule that no story would
exercise, behind a type promising it works. `aspectRatios` carries Backpack's
whole 18-value union instead, because there the mapping is generic — one rule per
_shape_ of value, not per value — so a contract test covers every member. That
does not reach past the issue's "no new aspect ratio Backpack's stories do not
use": every member is Backpack's own (`additional-types.ts:193-211`), so none of
them is new, and only the ones its stories name have a story here. Backpack's breakpoint
prefixes become five custom properties read by min-width queries at 768 / 1024 /
1264 / 1440px, with `s` as the no-query base, which is Backpack's own
arrangement.
